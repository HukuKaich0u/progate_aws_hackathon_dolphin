# フロントエンド技術方針

## 概要

このプロダクトのフロントエンドは、単なる画面表示ではなく、音声録音、音声再生、リアルタイム通話、通知起点の再接続まで含む音声体験の中核を担います。

そのため、通常の CRUD 中心アプリよりも、音声デバイス制御とリアルタイム通信の安定性を優先します。

## 推奨方針

- 音声コアを重視するなら `Swift` を第一候補にする
- もしクロスプラットフォームの開発速度を優先するなら、`React Native` を使いつつ音声コアだけはネイティブ実装に分離する
- Web は補助クライアントとして使い、録音プロフィール編集、候補探索、運用画面に寄せる

このプロダクトでは、録音プロフィールとリアルタイム通話の両方が主要機能です。そのため、音声体験を素直に作れる `Swift + AVFoundation + WebRTC native` の構成が最も筋がよい選択です。

## 候補スタック

### iOS ネイティブ案

- `Swift`
- `SwiftUI`
- `AVFoundation`
- `CallKit`
- `PushKit`
- `WebRTC iOS native stack`

この構成は、録音、再生、オーディオセッション、Bluetooth 切り替え、バックグラウンド制御、通話制御を一貫して扱いやすいのが利点です。

### ハイブリッド案

- `React Native`
- 音声コアは `Swift`
- 状態管理は `Zustand` または `Redux Toolkit`
- API 通信は `REST` または `gRPC-web`

この構成は UI 開発速度が高い一方、音声アプリでは結局ネイティブブリッジの実装が増えやすいです。音声体験がプロダクトの中心なら、純粋な React Native だけで完結する前提は置かない方がよいです。

## 主要機能と責務

### 録音プロフィール

- 音声録音
- 録音レビュー再生
- アップロード前の最低限の品質確認
- 音声プロフィール作成フロー

### リアルタイム通話

- 通話待機
- マッチ成立後の接続
- 通話中 UI
- ミュート、切断、再接続
- 通話品質の状態表示

### 補助機能

- 候補一覧
- マッチ履歴
- 通知
- 通報
- 設定

## フロントエンドで気をつける点

### 音声制御

JS レイヤーをまたぐ回数が増えると、通話中の状態遷移や録音制御の不具合が追いにくくなります。録音、再生、通話制御はできるだけネイティブ側で責務を閉じる方が安全です。

### リアルタイム接続

UI 状態と WebRTC 状態を分離し、接続状態、ICE 状態、メディア状態を明示的に管理します。表示ロジックと通話セッション制御を密結合にしないことが重要です。

### 計測

音声機能ではクラッシュ率だけでなく、録音成功率、通話接続成功率、通話継続時間、切断率、再接続成功率を計測対象に含めます。

## Web の位置づけ

Web は主クライアントにするより、次の用途に向いています。

- 録音プロフィール作成
- 候補探索
- 管理画面
- モデレーション画面
- 分析ダッシュボード

リアルタイム通話をモバイルブラウザ中心で成立させることは可能ですが、通知起点の UX、バックグラウンド挙動、音声制御の自然さではネイティブアプリより不利です。
