# Rust Backend: AI コーディングと相性のいい設計・技術選定メモ

## 目的

Rust でバックエンドを書くときに、AI と人間のどちらにとっても扱いやすい構成を先に固定する。

このメモの狙いは次の 3 つです。

- 責務と依存方向を明確にして、AI に局所的な変更をさせやすくする
- Rust 特有の複雑さを、所有権・非同期・抽象化の境界で暴発させない
- 将来の拡張性は確保しつつ、最初から過剰設計にしない

## 結論

Rust では、Go のようにクリーンアーキテクチャを全面適用するよりも、次の方針のほうが AI コーディングと相性がいい。

- モジュラモノリスから始める
- `feature-first` で機能単位に分割する
- ドメインは普通の `struct` / `enum` を中心に書く
- `trait` は外部境界だけに使う
- HTTP / DB / 外部 API の変換を明示する
- 非同期境界を薄く保つ

一言で言うと、Rust では「厳密な抽象化を増やす」より「境界と型を明示する」ほうが強い。

## システムデザイン方針

最初はマイクロサービスではなく、単一デプロイのモジュラモノリスを前提にする。

- API サービスは 1 つの Rust バイナリから始める
- データストアはまず 1 つの RDB を前提にする
- 外部 API 連携はアダプタ層に閉じ込める
- 非同期ジョブが必要なら、最初は同一リポジトリ内の別バイナリか単純なワーカーで十分
- gRPC、Kafka、CQRS、イベントソーシングは明確な要件が出るまで入れない

AI 観点では、デプロイ単位と依存関係が少ないほど、修正範囲を狭く保ちやすい。

## 推奨アーキテクチャ

クリーンアーキテクチャの精神は保ちつつ、Rust 向けに少し実装寄りへ寄せる。

- `handler`: HTTP の入出力変換だけを担当する
- `usecase`: アプリケーションの流れを担当する
- `domain`: 業務ルールと中心の型を持つ
- `repository`: 外部境界の `trait` を定義する
- `infra`: DB や外部 API の実装を置く
- `dto`: リクエスト / レスポンス / 永続化変換を明示する

### 推奨ディレクトリ例

```text
backend/
  src/
    main.rs
    app/
      mod.rs
      router.rs
      state.rs
    features/
      users/
        mod.rs
        handler.rs
        usecase.rs
        domain.rs
        repository.rs
        dto.rs
        error.rs
        tests.rs
      auth/
        mod.rs
        handler.rs
        usecase.rs
        domain.rs
        repository.rs
        dto.rs
        error.rs
    infra/
      db/
        mod.rs
        users_repository.rs
      external/
        mod.rs
        mailer.rs
```

この構成で重要なのは、機能単位でファイルの意味が固定されること。
AI に「`users/usecase.rs` だけ直す」「`users/handler.rs` でレスポンス変換を追加する」と依頼しやすくなる。

## Rust で特に意識する設計原則

### 1. `trait` は外部境界だけに使う

Rust では抽象化を増やしすぎると、ライフタイム、非同期、モック、関連型の複雑さが一気に増える。

そのため、`trait` は次のような差し替え点に限定する。

- Repository
- 外部 API クライアント
- キューや通知
- Clock
- ID 生成

逆に、ドメインロジックまで全部 `trait` 化するのは避ける。

### 2. ドメイン型・DB 型・API 型を分ける

同じ構造でも役割が違うなら分ける。

- API リクエスト/レスポンス型
- DB 入出力型
- ドメイン型

これを分けると変換は増えるが、責務は明確になる。
AI もどこで何を変えるべきか判断しやすい。

### 3. 非同期境界を薄くする

`async` を全レイヤに無差別に広げない。

- ハンドラは `async`
- UseCase は I/O を伴うなら `async`
- Repository 実装は `async`
- 純粋なドメインロジックは同期関数で保つ

同期で書ける処理まで `async` にしないほうが読みやすく、テストもしやすい。

### 4. 状態は `AppState` に明示的に寄せる

依存関係は `AppState` に集約し、各ハンドラやユースケースに明示的に渡す。

- DB pool
- Repository 実装
- Config
- 外部 API クライアント
- Logger / telemetry 関連

`Arc<Mutex<_>>` を何でも共有する形にはしない。

### 5. エラー型は層ごとに分ける

`thiserror` を使い、少なくとも次を分ける。

- ハンドラ層のエラー
- ユースケース層のエラー
- インフラ層のエラー

最終的な HTTP ステータス変換はハンドラ側で行う。
`anyhow` はアプリ境界や一時的な内部集約に限定し、コアの契約には持ち込まない。

## 推奨技術選定

2026-04-12 時点の初期選定案としては、次を基準にする。

- Web: `axum`
- Async runtime: `tokio`
- DB access: `sqlx`
- Serialization: `serde`
- Error: `thiserror`
- Logging / telemetry: `tracing`, `tracing-subscriber`
- Config: `.env` + 環境変数ベースのシンプルな構成
- Testing: 標準の `cargo test` を中心に、ユニットテストと最低限の統合テスト

### なぜ `axum`

- 構成が素直で、ハンドラの責務が見えやすい
- `State` や extractor の考え方が明快
- AI に局所修正を依頼しやすい

### なぜ `sqlx`

- SQL が見えるので、何を読んで何を書いているか追いやすい
- ORM に隠れた挙動が少なく、AI の修正が安定しやすい
- クエリ単位で責務を切り出しやすい

最初から重い ORM に寄せるより、`sqlx` で明示的にクエリを書くほうが、このプロジェクトでは相性がいい想定。

## AI コーディングと相性をよくするルール

実装時は、次のルールをできるだけ固定する。

- 1 ユースケース 1 ファイル
- 1 ファイル 1 責務
- `handler.rs` に業務ロジックを書かない
- `domain.rs` に HTTP 依存を持ち込まない
- Repository の戻り値・エラー型を毎回明示する
- DTO 変換は関数名か `From` 実装で一貫させる
- 例外的な設計はコメントで理由を書く
- まず 1 機能分の見本実装を人間が作り、それを AI のテンプレートにする

AI は「よい既存例」を真似するのが得意なので、最初の 1 機能で規約を固めるのが重要。

## 避けたいパターン

特に次のパターンは避ける。

- 全レイヤを interface / `trait` 前提で設計する
- 巨大な generic と関連型を多用する
- ドメイン型と DB 型と API 型を 1 つにまとめる
- `Arc<Mutex<_>>` で可変状態を何でも共有する
- ビジネスロジックをマクロの中に隠す
- 1 ファイルに handler / usecase / query を混在させる
- 早い段階でマイクロサービスへ分割する

Rust では、抽象化の増やしすぎが AI にとっても人間にとってもコストになりやすい。

## 実装の進め方

実装開始時は次の順序が無難。

1. `axum` の起動と `AppState` を作る
2. 1 機能だけ `handler/usecase/domain/repository/infra` の縦スライスで通す
3. その 1 機能を見本として他機能へ横展開する
4. テストパターンとエラーハンドリングを固定する
5. その後に認証、外部 API、ジョブ処理を足す

最初にすべての抽象を決め打ちせず、1 スライスで妥当性を確認してから広げる。

## このプロジェクト向けの暫定方針

現時点では、次の前提を採用する。

- バックエンドは Rust で実装する
- 最初はモジュラモノリスで始める
- Web フレームワークは `axum`
- DB アクセスは `sqlx`
- 機能単位のレイヤード構成を採用する
- AI に依頼しやすいよう、ファイル責務と依存方向を固定する
